# Развёртывание и восстановление

FIREBALL CMS 1.8.2 — стабильный релиз с исправлениями безопасности, платежей и обновлений. Ниже описаны требования сервера, установка, переход с предыдущих версий и восстановление после сбоя.

## Сервер

Требуются PHP ≥ 8.2, PDO MySQL, DOM, Fileinfo, OpenSSL, cURL, ZIP и функции multibyte strings; Composer поставляет совместимый polyfill. Рабочая БД и резервирование поддерживают InnoDB. Автоматическая полная копия требует доказуемой видимости метаданных: явный ALL PRIVILEGES на целевую БД либо глобальный ALL без частичных REVOKE. Учётные записи с ограниченными правами или правами через роли могут скрывать triggers/routines; для них используйте отдельное резервирование и ручное развёртывание. Не расширяйте права веб-учётной записи только ради автоматического updater. Автоматический updater откажется запускаться при наличии MyISAM, views, triggers, procedures/functions, events или символических ссылок в резервируемых каталогах: для этих конфигураций требуется отдельная процедура развёртывания и восстановления.

Document root должен указывать на `public`. Настройте [Apache](apache.conf) либо [Nginx](nginx.conf), PHP и HTTPS для своего сервера. Примеры не настраивают сертификат, PHP-FPM на Apache или HTTP→HTTPS redirect автоматически. Проверьте конфигурацию средствами своего сервера до перезапуска. Настройте одинакового владельца/права для web PHP и CLI; нужны запись в `storage`, `tmp`, `public/uploads`, а для установки и обновлений также в конфигурацию и каталоги приложения. `config.local.php`, SQL/ZIP резервные копии и recovery descriptor должны иметь права `0600`.

В `config/config.local.php` задайте `PATH` — полный канонический HTTP(S)-адрес сайта, включая подкаталог при его использовании. Настройте `TRUSTED_PROXIES` только для действительно доверенных прокси. Ссылки больше не переключаются на произвольный Host запроса. Установка через другой адрес требует правильного `PATH`. Текущий файловый лимитер и файловые блокировки рассчитаны на один сервер с общим локальным хранилищем; несколько независимых узлов требуют общего механизма лимитов и согласованного обслуживания.

## Обновление

Обновление сохраняет локальную конфигурацию, пользовательские загрузки, `storage` и `themes/custom`. Пакет включает проверенные версии встроенных плагинов; `release-plugins.json` фиксирует версии и контрольные суммы их исходников. Независимые обновления плагинов продолжают поступать из их настроенной ветки `main`, поэтому после такого обновления состав уже отличается от состава пакета.

Перед первым переходом со старого выпуска остановите публичный трафик и фоновые процессы на уровне сервера: предыдущие версии ещё не используют новую раннюю блокировку. Даже после перехода остановите сторонние workers, которые обращаются к БД в обход `public/index.php` и `bin/cms.php`. Штатные входы новой версии получают общую блокировку до загрузки приложения. Обновление получает исключительную блокировку и откажет, если ещё выполняется запрос или команда; повторите запуск после их завершения.

Резервная копия перед обновлением включает код, зависимости, конфигурацию и данные. Для SQL используется согласованный snapshot; записи в поддерживаемых входах при обновлении остановлены. Место для SQL, полного ZIP, распаковки и восстановления необходимо обеспечить заранее. Неполная резервная копия прерывает обновление до изменения установки. Внешние архивы храните согласно своей политике доступа и шифрования.

Если обновление изменило установку и завершилось ошибкой, сайт сохраняет HTTP 503. Маркер `storage/update.maintenance` не удаляется автоматически по времени. Кнопка отката только кода отключена: она не отменяет миграции БД.

## Первый переход с 1.8.0 или старого updater

Минимальная поддержанная исходная версия этого пакета — 1.8.0; более старую установку сначала переведите на 1.8.0 и проверьте её резервное восстановление. Старый Git-валидатор отклоняет новые и защищённые пути ещё до загрузки исправленного кода. Для первого перехода используйте `bin/upgrade-local.php` из **распакованного нового ZIP**, расположенного вне каталога работающей установки. Остановите публичный трафик и все фоновые процессы на уровне сервера, проверьте контрольную сумму пакета и выполните:

```sh
# Для установки без Git:
php /srv/releases/fireball-1.8.2/bin/upgrade-local.php --root=/srv/fireball --confirm-offline

# Для Git-установки сначала получите опубликованный доверенный тег:
git -C /srv/fireball fetch origin tag 1.8.2
php /srv/releases/fireball-1.8.2/bin/upgrade-local.php --root=/srv/fireball --ref=1.8.2 --confirm-offline
```

Команда использует новый updater из пакета: проверяет требования и манифест, создаёт полные снимки, обновляет Git только fast-forward, сохраняет локальные данные, устанавливает код и запускает миграции/переиндексацию. Она не получает тег из сети самостоятельно. Манифест полученного Git-тега должен совпадать с манифестом пакета; локальные изменения кода предварительно сохраните. Если снимок или preflight не проходит, установка не меняется. Если ошибка возникает после начала изменения, обслуживание остаётся включённым и применима описанная ниже процедура восстановления. После успеха перезапустите PHP и проверьте сайт до возврата трафика.

## Восстановление после ошибки

Сохраните журнал ошибки и не возобновляйте публичный трафик или фоновые задачи. Под тем же владельцем файлов выполните:

```sh
php bin/recover-update.php --confirm
```

Команда работает без загрузки приложения, проверяет контрольные суммы `storage/update-recovery.json` и восстанавливает **код и БД** из последнего снимка. Она доступна только при активном обслуживании и свободной исключительной блокировке. Успех снимает обслуживание; ошибка оставляет его включённым. Перезапустите PHP-FPM/Apache после восстановления, чтобы сбросить OPcache всех процессов, и проверьте сайт перед возвратом трафика.

Если bootstrap, CLI восстановления или файловые права повреждены, используйте ручное восстановление обоих архивов из `storage/backups` на выключенном сайте. Сначала восстановите доступ к сохранённой конфигурации и инструментам восстановления. Не удаляйте marker вручную ради обхода ошибки и не восстанавливайте старую БД после возобновления продаж: потеряются новые операции. Автоматический recovery рассчитан именно на прерванное обновление до возврата трафика.

## Релизные проверки из репозитория

```sh
composer install
php tools/build-release.php
php bin/check-release.php --browser --mysql --composer
FIREBALL_RELEASE_ZIP="$PWD/dist/fireball-cms-1.8.2.zip" php tests/release_install_recovery_mysql.php
```

Для браузеров нужен Playwright 1.48.2 с Chromium/Firefox. `FIREBALL_PLAYWRIGHT_MODULE`, `NODE_PATH`, `PLAYWRIGHT_BROWSERS_PATH` и `FIREBALL_PHP` позволяют задать тестовое окружение; `FIREBALL_NODE` и `FIREBALL_COMPOSER` — пути инструментов. MySQL-проверка создаёт и удаляет случайную локальную базу `fbl_release_test_*`; используйте отдельный тестовый сервер и учётную запись с CREATE/DROP DATABASE. Настройки берутся из локальной конфигурации либо `FIREBALL_TEST_MYSQL_HOST/PORT/USER/PASSWORD`. Нелокальные адреса тест отклоняет.

До публикации отдельно проверьте sandbox платёжного провайдера, VPN-интеграции, настоящий HLS, Safari/iOS и переход с реально установленного предыдущего стабильного выпуска. Изолированные проверки с подменённым провайдером не подтверждают работу этих внешних систем.
