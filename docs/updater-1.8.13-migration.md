# FIREBALL CMS 1.8.13: обновления, PWA и независимые плагины

## Что изменилось

Стандартный набор `public/assets/default/pwa/` принадлежит релизу CMS. Сохранение настроек больше не генерирует туда картинки. Пользовательские изображения и сгенерированные наборы находятся в защищённом `public/uploads/pwa/`. Наборы `generated-<SHA256 исходника>` публикуются целиком через временный каталог; чтение страницы не запускает генерацию. Для генерации PNG требуется GD. SVG остаётся SVG favicon; для Apple Touch Icon и Android используются корректно описанные растровые размеры.

Изменения настроек в БД, `config/config.local.php`, `storage/`, загрузки, музыка, `themes/custom/`, локальный Composer и его учётные данные сохраняются. Локальные `composer.lock` и `vendor/` считаются управляемыми зависимостями: после резервирования они приводятся к состоянию Git, затем устанавливается согласованный с релизом набор зависимостей. Более свежий Composer или результат обычного `composer install` больше не является конфликтом исходников. Ручная правка `composer.json` остаётся конфликтом.

Установка или административное обновление плагина создаёт приватную запись `storage/component-installations/plugins/<slug>.json`: SHA256 каждого файла и источник пакета. Движок сохраняет такой каталог целиком, включая установленную версию, и проверяет его после обновления. Сам плагин обновляется отдельным административным действием. Правки кода после установки нарушают соответствие записи и блокируют замену. Перед заменой плагина состав файлов проверяется повторно, затем новый пакет сверяется после миграций. Не следует хранить изменяемые данные внутри каталога плагина; для них предназначены `storage/` и `public/uploads/`.

Плагины старой Git-установки без записи о пакете распознаются как административное обновление только при полном совпадении файлов с полученной из `origin/main` версией, которая новее версии в локальном HEAD. Совпадения одного номера версии недостаточно. Новые плагины, отсутствующие в HEAD, сохраняются отдельно. В ZIP-установке уже существующие каталоги плагинов не заменяются обновлением движка. Для старого ZIP-плагина без записи обновлятор сравнивает все файлы с официальным историческим пакетом той же версии: сначала использует сохранённый коммит установки, затем ограниченную историю из 20 изменений `plugin.json` в main. Совпадения версии недостаточно. Если пакет не найден или содержит другие файлы, возникает явный конфликт; неизвестные правки не объявляются штатными.

## Уже изменённые стандартные PWA-иконки

При Git-обновлении принимается только конечный список штатных PNG/ICO с корректным форматом и размерами. Произвольные файлы, PHP под видом PNG и символические ссылки блокируются.

После проверки и создания копий **кода и БД** старый полный набор копируется из проверенного ZIP-снимка в `public/uploads/pwa/legacy-<SHA256 набора>/`. Если сайт использовал системные растровые картинки, активный набор переключается на сохранённую копию. Существующий пользовательский набор сохраняет приоритет. Ссылки настроек на старые стандартные картинки переводятся на сохранённые изображения. Настройки выбора связаны с отпечатком конфигурации; новый пользовательский источник не подменяется старой миграцией.

Только после сохранения и проверки копий изменённые отслеживаемые файлы возвращаются к локальному HEAD, выполняется fast-forward до заранее проверенного коммита, а защищённые файлы восстанавливаются из снимка. `git reset --hard` не используется. Изменение файла после резервирования останавливает замену.

Для ZIP-обновления старый системный набор сохраняется при отличии от пакета. Без Git нельзя достоверно отличить старую штатную картинку от пользовательской, поэтому используется сохранение прежнего вида. Повторное обновление не меняет уже выбранный пользовательский набор.

## Обычное обновление из main

1. После публикации релиза в `Samkmv/FIREBALL_CMS`, ветка `main`, открыть административный центр обновлений и проверить обновления.
2. Обновлятор получает и фиксирует конкретный коммит, проверяет ветку, локальные изменения, `update.json`, минимальную версию CMS, PHP-синтаксис и требования независимых плагинов.
3. Под общей блокировкой и в режиме обслуживания создаются приватные согласованные копии БД и файлов. В `storage/update-recovery.json` сохраняются пути, SHA256 и исходный Git-коммит.
4. Выполняются миграция старых иконок, подготовка управляемых файлов, fast-forward, восстановление защищённых файлов, согласование Composer и миграции БД.
5. Проверяются версия, установленный коммит, основные входные файлы, зависимости и сохранённые пакеты плагинов. Успех снимает режим обслуживания; ошибка после начала замены сохраняет его для восстановления.

Реальный конфликт PHP-кода, изменённый пакет плагина, незавершённый Git-конфликт, неподтверждённая резервная копия и несовместимость не обходятся автоматически.

## Однократное внедрение, если старый обновлятор уже заблокирован

Старый код обновлятора сам не получит это исправление, пока блокирует обновление. После публикации **именно этой версии в main** можно один раз установить следующие файлы из одного и того же официального архива через файловый менеджер хостинга:

- `app/Services/UpdateCenter.php`
- `app/Services/UpdateRecoveryService.php`
- `app/Services/PluginUpdateService.php`
- `app/Services/PwaService.php`
- `app/Services/PwaIconStorage.php`
- `app/Services/ManagedPluginInstallations.php`
- `core/Plugins/PluginManager.php`

Перед этой ручной заменой создать резервную копию **всего сайта и БД средствами хостинга** и временно закрыть доступ к сайту на время замены всех семи файлов. Не заменять загрузки, стандартные PWA-картинки, `config.local.php`, музыку или содержимое БД. Затем открыть админку, выбрать канал main и выполнить проверку и обновление.

Новый обновлятор принимает эти семь файлов как официальный bootstrap **только при побайтовом совпадении с уже полученным `origin/main`**. Они резервируются и безопасно согласуются с Git перед установкой полного коммита. Любое отличие от официального кода остаётся конфликтом. До публикации исправления в main этот способ не разблокирует произвольную локальную сборку.

## Восстановление

После неудачи не удалять `storage/update.maintenance` и не повторять обновление поверх незавершённого. Сохранённые копии защищены контрольными суммами; обычная очистка старых копий не удаляет активный снимок восстановления.

Из консоли хостинга, в каталоге сайта:

```sh
php bin/recover-update.php --confirm
```

Это офлайн-восстановление одновременно возвращает код, БД и Git-метаданные к снимку перед обновлением, удаляет введённые неудачной версией файлы/таблицы/служебные записи пакетов и восстанавливает триггеры после загрузки строк. При успехе снимается обслуживание. При ошибке оно сохраняется; резервные копии остаются доступными для восстановления средствами хостинга. Не требуется вручную исправлять Git после обычной смены иконки, установки зависимостей или обновления плагина.

## Автоматические проверки

PHP 8.2+, Git и ZipArchive:

```sh
php tests/update_center_git.php
php tests/update_center_dependencies.php
php tests/update_center_runtime.php
php tests/update_center_recovery.php
```

Последний сценарий также использует GD, локальный Composer (`/usr/local/bin/composer`, другой путь задаётся через `FIREBALL_TEST_COMPOSER`) и настроенный MySQL с правом создать/удалить отдельную тестовую базу. Создаётся уникальная БД `fbl_update_test_<случайный идентификатор>`; рабочая БД сайта не используется. Composer работает без сети с локальным тестовым пакетом. Сетевые ответы GitHub для административного обновления плагина подменяются тестовым архивом; сам сервис установки, проверки, резервирования и миграции выполняется настоящий.

Все файлы проверок создаются в `tests/.tmp/` и удаляются после завершения. Отчёты находятся в `tests/artifacts/update-center/`. Проверены реальные fast-forward, `composer install`, административная замена плагина, перенос старых иконок, сохранность пользовательской музыки и настроек, блокировка исходного кода, прерывание миграции после DDL и полное восстановление.
