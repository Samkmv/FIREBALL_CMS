# Исправления перед выпуском FIREBALL CMS 1.8.2

Дата завершения: 4 октября 2026 года. Основа: `main`, коммит `0b74e07`, исходная версия `1.8.2-beta.35`. Изменения находятся в рабочем дереве; тег и GitHub Release не опубликованы.

Подготовлен локальный пакет 1.8.2. Найденные опасные пути исправлены, добавлены проверки и отдельный безопасный переход со старого updater. Публикация требует проверки выбранного сервера и реальных внешних интеграций, перечисленных ниже. Это результат исправлений [исходного аудита](release-audit-2026-10-03.md), а не обещание отсутствия любых других ошибок.

## Проверки

- PHP: 67/67 наборов на PHP 8.2 и 8.4; включают исходные 64 и новые security, payment/search, recurring retry.
- JavaScript: 13/13 наборов.
- Браузер: 8/8 наборов. В установленном тестовом окружении используются Chromium 130 и Firefox 131; это не проверка актуальных браузеров пользователей, Safari или настоящего HLS.
- Новые проверки: security 62, payment/search 16, recurring retry 11, установка/recovery/concurrency MySQL 30, переход Git/ZIP с 1.8.0 — 15 утверждений.
- MySQL-интеграции создают и удаляют случайные локальные базы `fbl_release_test_*`. Рабочая БД не обновлялась и не использовалась для пробной установки/восстановления.
- Полный синтаксис собственных файлов проверен на PHP 8.2/8.4 и Node 24; новые CLI/интеграционные файлы дополнительно проверены после добавления.
- Composer: validate/check-platform/audit проходят на MAMP PHP 8.2, известных advisories нет; install --dry-run не предлагает изменения зависимостей.
- Текущий MAMP: 10 гостевых страниц HTTP 200 без ошибок JS, неудачных загрузок и горизонтального переполнения на 1440/390/320. Четыре внутренних пути дают 403.
- Проверен отдельно Apache с document root public. Nginx, PHP-FPM и реальные HTTPS/proxy-настройки выбранного production-сервера требуют проверки на нём.

## Пакет и переход

Артефакт: `dist/fireball-cms-1.8.2.zip`; рядом `.sha256`. Сборщик сверяет содержимое каждого файла с текущим источником и записывает версии/хэши пяти встроенных плагинов. В пакет включены runtime, vendor, установочные SQL, минимальные runtime placeholders и инструкция deployment; тесты и локальные данные не включены.

Первый переход со старого Git-updater выполняется командой из распакованного нового пакета, размещённого вне установки. Для Git нужен заранее полученный доверенный тег и --ref; Git обновляется только fast-forward. Остановка публичного трафика и всех workers обязательна. Команда проверена на исходниках и схеме 1.8.0 с моделируемым новым release commit, а также на установке без Git. Опубликованного настоящего тега 1.8.2 пока нет.

Инструкция: [развёртывание, первый переход и recovery](deployment/README.md). Старый небезопасный откат только кода отключён. Полный recovery доступен до возврата трафика; после возобновления продаж откат старой БД потеряет новые операции. После CLI-перехода/восстановления перезапустите PHP и проверьте сайт перед возвратом трафика.

## Условия перед публикацией

1. Пройти сценарии sandbox платёжного провайдера: повторные/поздние callback, timeout, подписи и повторное списание. Проверки состояний в этом отчёте не выполняют настоящий платёж.
2. Проверить предусмотренные VPN-интеграции и настоящий медиапоток; Safari/iOS/PWA/Web Push и актуальные версии Chromium/Firefox.
3. Проверить выбранный сервер: HTTPS PATH, доверенные proxy, владельцы файлов/прав, OPcache, nginx/php-fpm при их использовании, место под резервирование и остановку сторонних workers. Для ограниченной DB account автоматическое резервирование намеренно запрещено; нужен отдельный deployment-процесс.
4. Повторить переход и recovery на staging-копии с характерными существующими данными. Проверить исторические дубликаты аренды и бизнес-состояния, которые не следует удалять автоматически.
5. Зафиксировать проверенный коммит, дождаться CI, согласовать тег/версию/контрольную сумму публикуемого ZIP. Файл не опубликован и на production не развёрнут.

## Следующие улучшения

Очередь доставки Push с общим бюджетом, атомарный лимит endpoint, общий backend rate limits для нескольких узлов, нагрузочное тестирование и мониторинг, расширенное резервирование views/triggers/routines/events и ролей, staging-матрица исторических данных. HSTS/CSP следует настроить под реальное HTTPS-развёртывание и необходимые ресурсы редактора после проверки совместимости. Эти улучшения не представлены как уже реализованные.
