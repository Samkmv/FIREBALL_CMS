# Доступ к источникам обновлений плагинов — CMS 1.8.29–1.8.30

## Исправление установки старых пакетов в 1.8.30

Следующий снимок Maxipapa показал ограничение GitHub уже при установке трёх найденных обновлений. Исправление 1.8.29 убрало обязательный REST API из получения новых версий и архивов, но поиск исходного пакета старой ZIP-установки без сохранённого подтверждения всё ещё использовал историю коммитов и деревья API. Это была оставшаяся зависимость, а не ошибка самих трёх плагинов.

В 1.8.30 вместе с ядром поставляется `config/plugin-baselines.json`: 210 уникальных состояний 151 версии шести встроенных плагинов из истории, достижимой из официального коммита `3302f4b9ae6513985513cb0a7fe5fd0874d44a29`. Это продуктовые контрольные суммы, не временный тестовый файл. Они покрывают в том числе Tape Room 1.7.6, «Подписки» 1.5.4 и «Прокат машинок» 1.1.11.

`PluginBaselineCatalog` сверяет репозиторий, путь, версию и SHA256 каждого обязательного файла исторического архива. Дополнительные файлы исходной Git-копии допускаются только при совпадении с тем же коммитом; объединять разрешения разных состояний нельзя. Изменённые, отсутствующие и неизвестные файлы не получают разрешение на замену. Существующие конфликты Git и ранее сохранённых подтверждений проверяются раньше каталога и не обходятся. Подтверждение новой установки записывается лишь после штатного успешного обновления.

Для таких старых официальных пакетов больше не нужны ни история REST API, ни Git на сервере. Перед атомарной заменой повторно проверяется тот же исходный снимок файлов. Ограничения размера JSON, числа файлов, путей и символических ссылок сохраняют закрытое поведение при повреждённом каталоге. Для сторонних репозиториев и неизвестного состава остаётся прежняя проверка источника — принудительного одобрения по одному номеру версии нет.

Проверены 288 сценариев: 87 проверок исходных пакетов и каталога, 66 транспорта, 19 Git, 29 зависимостей, 51 сохранения рабочих данных и 36 установки/восстановления. В последнем наборе реально установлено обновление старого ZIP-плагина на отдельной тестовой MySQL, когда все REST-узлы возвращали 403 и был задан устаревший токен: выполнены только публичные HEAD/raw/codeload-запросы, записано новое подтверждение и завершён режим обслуживания. Для трёх перечисленных версий контрольные суммы дополнительно сопоставлены с настоящими Git-объектами и историческими `git archive`.

Новых одноразовых тестовых файлов не оставлено; регрессии дополнены в существующих наборах. После публикации владельцем требуется обновить **ядро до 1.8.30**, затем повторить обновление плагинов. Боевой сайт в этих проверках не изменялся.

## История изменения 1.8.29

## Что воспроизведено

На скриншоте Maxipapa все шесть плагинов показывают «Источник обновления плагина недоступен». Это ошибка проверки источника, до скачивания и проверки исходного пакета.

В прежнем коде одна проверка шести плагинов требовала 12 REST-запросов GitHub: шесть одинаковых запросов состояния ветки и шесть манифестов. Ошибки HTTP 401, 403, 404, 429 и 500 скрывались за одним текстом, а неудачный результат автоматически перепроверялся только через шесть часов. Эти дефекты воспроизведены изолированными тестами.

GitHub связывает неавторизованную REST-квоту с исходящим IP сервера, а не доменом: [официальная документация](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). Поэтому сайты на разных серверах или с разными токенами могут вести себя по-разному. Неверный токен тоже мог блокировать доступ даже к публичному репозиторию.

**Какой именно ответ получил сервер Maxipapa, по старому сообщению определить невозможно.** Доступа к его закрытой диагностике при разработке не было. Ошибка сайта не объявляется доказанным ограничением квоты: для её точного подтверждения нужен ответ его сервера после выкладки или соответствующий журнал.

## Изменения

- Публичная ветка определяется через HTTPS Git `info/refs` один раз на пакетную проверку; манифесты читаются через `raw.githubusercontent.com` по одному неизменяемому SHA коммита. Необязательный токен туда не отправляется.
- Новый пакет и исходный пакет для проверки скачиваются через `codeload.github.com/…/zip/{SHA}`. Адрес не содержит `refs/heads/`, и смена ветки между проверкой и скачиванием не меняет выбранный пакет.
- Для приватных репозиториев и недоступных публичных узлов сохранён API-вариант. Все прежние ограничения HTTPS, адресов, перенаправлений, размеров, ZIP, совместимости, резервирования и атомарной замены продолжают действовать.
- HTTP 401, запрет доступа, отсутствие файла, ограничение запросов, ошибка сервера и ошибка соединения теперь различаются. Произвольное тело ответа, токены и внутренние сетевые подробности в сообщение не копируются. Переводы есть на четырёх языках.
- Успешный результат хранится шесть часов, ошибка проверки — пять минут. Если GitHub сообщил `Retry-After` или срок восстановления квоты, автопроверка ждёт этого срока, с защитным пределом 24 часа. Заголовки промежуточного ответа не переносятся в окончательный.
- Поиск неизвестного исходного пакета по истории и подтверждение дополнительных Git-файлов всё ещё могут требовать REST API. При его отказе проверка останавливается с конкретной причиной: обхода защиты локальных файлов и принудительного обновления нет.
