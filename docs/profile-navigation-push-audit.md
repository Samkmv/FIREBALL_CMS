# Profile navigation and device-scoped Push — 2026-10-05

## Audit

Profile routes remain `/profile` and `/profile/settings?section=information|security|notifications`.
`AuthController::settings()` calls the existing `profile(true)` method; it normalizes the section
and passes `is_settings` / `settings_section`. Both routes share the same profile partial.
There is a theme partial and a legacy fallback, not separate menus for each page.
Plugin services continue to use the existing `profile_menu` hook in the sidebar.

Push chain: public layout data attributes → `public/assets/default/js/pwa.js` → active
ServiceWorkerRegistration / PushManager → `/api/pwa/subscriptions`,
`/api/pwa/subscriptions/delete`, `/api/pwa/status` → `PwaController` → `PwaService`.
Worker source is generated by `PwaService::serviceWorkerScript()`; `/sw.js` and
`/service-worker.js` route to it. `public/service-worker.js` is a compatibility wrapper.

Storage already supports multiple endpoints in `pwa_subscriptions` (unique endpoint hash,
user ID, active/revoked flags and browser keys). `notification_settings.push_enabled` is an
aggregate delivery flag, not proof that this browser has a subscription. No schema change is needed.

Confirmed causes:

1. The active theme layout did not pass `data-pwa-auth-user-id` or `data-pwa-status-url`.
   PWA treated signed-in users as guests, hid buttons and cleared the local app badge.
2. Overview inferred enabled from the total number of active endpoints on **any** device.
   Only the settings badge was updated by JavaScript.
3. Button visibility depended on a separate iOS/standalone rule instead of actual Push state.
4. The permission flow awaited worker registration before requesting permission, risking loss
   of Safari's user activation.
5. Page-load status synchronization POSTed the endpoint, potentially reactivating a revoked
   subscription or reassigning a shared browser endpoint without an explicit Enable action.
6. HTTP 200 was treated as success even when the JSON payload had `status: false`.
7. The theme draws `nav-underline` below the link box. Horizontal overflow clipping needs
   the standard `pb-1` utility to leave its underline visible.

## State and actions

Enabled requires supported APIs, HTTPS/local development, configured PWA/Push/VAPID,
granted permission, an actual browser subscription using the current VAPID key, an active
server endpoint owned by the current user and enabled delivery. Other devices cannot satisfy it.
Missing endpoint / unregistered endpoint: disabled + Enable. Denied: blocked with browser/OS
instructions and no permission button. Unsupported: explanation; on iOS outside standalone,
the Home Screen installation explanation. Network/worker failure: error, not falsely enabled.

Enable calls `PushManager.subscribe()` directly inside a user gesture; this API performs the
permission request. The active worker is prepared beforehand. The endpoint is saved through
the existing CSRF-protected API. VAPID key rotation uses one cleanup action followed by a new
click, preserving Safari user activation. Disable deactivates only the current user's endpoint
and unsubscribes it in the browser; aggregate delivery remains enabled if another device exists.
Read-only checks on page load/return never resubscribe or reactivate endpoints.

In-site notifications remain a separate channel. No theme style redesign, manifest changes,
worker delivery changes, DB migrations or plugin changes/version bumps were needed.

## Verification and deployment

Run:

```sh
php tests/profile_push_unit.php
node tests/profile_push_browser.cjs
php bin/cms.php assets:rebuild
```

Browser test requires Playwright/Chromium; `PHP_BIN` can select the PHP executable.
Checks cover direct/reloaded routes in ru/en/de/zh-cn, active-item visibility, horizontal
scroll, pill active borders, vertical theme tabs and hover animation, danger logout, mobile touch size, light/dark and theme/fallback rendering;
desktop enable/disable/reload; blocked permission, denied prompt, failed save/status/worker;
overview/settings consistency; two-device isolation; iPhone/iPad/Android environment branches.

Push APIs, permission results and backend responses are test doubles. **Physical iOS/Android
PWA installation, native permission dialogs and real APNs/FCM delivery are not verified by
these tests.** Run those smoke tests on a staging HTTPS installation with its VAPID keys.
Safari activation constraints follow [Apple's Web Push documentation](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).

The local asset manifest was rebuilt. Worker source/cache policy is unchanged: CSS/JS URLs
are content-versioned and the worker caches them by full URL. Thus no worker cache-version
bump is needed. A manual Git deployment **must** run `assets:rebuild`; the CMS updater already
does this. Old open pages need reloading; do not ask users to revoke/reinstall working subscriptions.

Scope risk: custom themes that override profile/layout partials must adopt the same data
attributes. Shared-browser account switching now requires an explicit Enable action to assign
an endpoint to a different account, rather than assigning it silently on page load.

## Admin PWA device management follow-up

Previously `devices()` displayed at most 100 rows, including inactive bindings, without
pagination, status or management actions. The new `paginatedDevices(20)` uses the existing
CMS Pagination (`devices_page`) and selects only display fields, not endpoint URLs or keys.
The original `devices()` method remains for compatibility.

Changed: `app/Controllers/AdminController.php`, `app/Services/PwaService.php`,
`config/routes.php`, `app/Views/themes/default/admin/pwa_settings.php`,
new `admin/partials/pwa_devices.php`, and base translations in ru/en/de/zh-cn.
The table reuses CMS table/footer/mobile-card partials and the standard confirmation modal.
Desktop shows a full-width table; mobile uses the CMS cards. Both detach buttons have
44px minimum touch height. The history of sent notifications is unchanged.

The POST route requires authentication, admin authorization and the router's default CSRF.
Explicit `scope=one` requires a positive device ID; only `scope=all` removes every binding,
across all users and pages. Missing or malformed IDs cannot imply all. A transaction locks
the selected bindings, deletes those exact records and recomputes affected user flags from
remaining active subscriptions. Failures roll back both bindings and flags. Successful POST
returns to page one and the device-table anchor, avoiding a deleted last page.

These records are browser Push bindings, not a unique hardware inventory: one phone can have
separate Safari/PWA/browser bindings. Server removal stops future delivery through CMS and
removes rows; it cannot remotely revoke OS/browser permission or erase already queued Push.
Read-only page-return status checks show disabled and do not recreate removed bindings.
Users can link a device again only through an explicit Enable action.

Verification: `tests/profile_push_unit.php` covers 126 records, pagination, single/all detach,
other-user isolation, last-device flag, rollback, malformed controller requests and translations.
`tests/pwa_devices_browser.cjs` / `tests/fixtures/pwa_devices.php` use real shared CMS templates,
pagination, modal and assets with isolated responses: desktop/mobile, four languages, cancel,
one/all confirmation, CSRF fields, row disappearance, last/empty pages and touch targets.
No real stored device was detached during QA. MySQL locking concurrency and physical iOS
Push delivery still require staging verification; SQLite/browser mocks do not prove those.

Final results: 541 PHP/service/controller checks, 268 profile/browser checks, and 128 admin
device-table/browser checks passed. PHP/JavaScript syntax and whitespace checks passed.
Profile CSS copies match; the rebuilt asset manifest was verified against current content hashes.
