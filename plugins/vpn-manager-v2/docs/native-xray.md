# Управление самостоятельным Xray-core

Версия плагина 3.3.0 добавляет способ управления **Xray-core · FIREBALL Agent** в существующий VPN-плагин CMS. На перенесённом сервере CMS обращается к нашему агенту по HTTPS. Агент выполняет ограниченный набор команд локального Xray API. Для агента нужны Python 3.9+ со стандартной библиотекой и системный OpenSSL 1.1.1+ или 3.x с поддержкой X25519 по пути `/usr/bin/openssl`. Проверенная версия API — Xray 26.11.9.

Клиенты, тарифы, порядок, внешние источники, постоянные URL подписок, токены и очередь операций продолжают использовать текущую базу `vpn_v2_*`. Выбранная интеграция задаётся для каждого сервера полем `auth_type`. Сохранённые способы `token` и `password` позволяют переносить серверы по очереди. Способ `xray` обращается только к FIREBALL Agent.

## Что подготовить

1. Сделайте резервную копию базы CMS, настроек плагина, базы прежней панели и полного серверного JSON Xray. В серверном JSON должны быть прежние UUID, пароли, порты, адреса, настройки транспорта, сертификаты и privateKey REALITY. Закройте доступ к резервным копиям.
2. Выберите отдельный Linux-сервер или тестовое входящее подключение для проверки. На рабочем сервере переход процесса на тот же порт может разорвать текущие соединения.
3. Установите официальный Xray с командами `api inbounduser`, `api adu`, `api rmu`, `api statsquery`, `api statsgetallonlineusers`, `api adi`, `api rmi`. Текущую сборку можно проверить командой `xray version`. Официальные установочные материалы доступны в репозитории [XTLS/Xray-install](https://github.com/XTLS/Xray-install).
4. Настройте отдельный systemd-сервис `xray.service`, использующий один JSON-файл `/usr/local/etc/xray/config.json`. Перенесите в него полный прежний JSON. Для существующих inbound сохраните тег вида `inbound-24`, где 24 — прежний remote inbound ID в CMS. Для новых подключений используйте свободные положительные числа.
5. При освобождении рабочих портов остановите прежний процесс Xray, которым управляла панель, и запустите самостоятельный. Убедитесь, что одновременно этот JSON редактирует только FIREBALL Agent. Сохраните резервную конфигурацию для возврата.

Основной адрес сервера в CMS участвует в формировании VPN-конфигураций клиентов. Сохраните его при переносе. Адрес агента вписывается в **отдельный API URL**. Например, VPN остаётся на `https://vpn.example`, а агент доступен по `https://control.example/fireball-xray`.

## Локальный API и статистика Xray

Включите эти разделы в полный серверный JSON, сохранив существующие inbounds, outbounds, routing, DNS и настройки безопасности.

```json
{
  "api": {
    "tag": "fireball-api",
    "listen": "127.0.0.1:10085",
    "services": ["HandlerService", "StatsService"]
  },
  "stats": {},
  "policy": {
    "levels": {
      "0": {
        "statsUserUplink": true,
        "statsUserDownlink": true,
        "statsUserOnline": true
      }
    }
  }
}
```

Это фрагмент для объединения с текущей конфигурацией. У сохранённых пользователей должны быть прежние `email`. Для пользователей с другим `level` включите сбор статистики и на этом уровне. Создаваемые агентом пользователи используют уровень 0.

После объединения проверьте полный файл и запустите подготовленный сервис.

```bash
/usr/local/bin/xray run -test -config /usr/local/etc/xray/config.json
sudo systemctl start xray.service
/usr/local/bin/xray api statssys --server=127.0.0.1:10085
```

Агент использует `systemctl show xray.service` и `/proc` для определения поколения процесса. Это позволяет отличать новые счётчики после перезапуска от уже учтённых. Накопленный расход хранится в SQLite агента и синхронизируется с CMS. При аварийном завершении Xray возможна потеря расхода после последнего успешного опроса агента, который выполняется раз в 5 секунд. Сохранённый в CMS расход используется как стартовая величина при переносе. Разница между последним опросом прежней панели и моментом передачи требует сверки перед переносом.

## Установка FIREBALL Agent

Скопируйте файлы из каталога `plugins/vpn-manager-v2/agent` на подготовленный VPN-сервер. Команды ниже выполняются на этом сервере из каталога со скопированными файлами.

```bash
sudo install -d -m 755 /opt/fireball-xray
sudo install -d -m 700 /etc/fireball-xray /var/lib/fireball-xray
sudo install -m 755 fireball_xray_agent.py /opt/fireball-xray/fireball_xray_agent.py
sudo install -m 644 fireball-xray-agent.service /etc/systemd/system/fireball-xray-agent.service
sudo sh -c 'umask 077; openssl rand -hex 32 > /etc/fireball-xray/token'
sudo systemctl daemon-reload
sudo systemctl enable --now fireball-xray-agent.service
sudo systemctl status fireball-xray-agent.service --no-pager
```

Токен из `/etc/fireball-xray/token` перенесите в поле токена сервера CMS через защищённое соединение. В CMS токен хранится зашифрованным. Файл токена на сервере доступен владельцу root. При изменении токена перезапустите агент и обновите токен в CMS.

Если Xray, его файл конфигурации или имя сервиса находятся по другим путям, задайте их в `ExecStart` через `--xray`, `--config`, `--service`. Скорректируйте `ReadWritePaths` в unit. Директория конфигурации должна быть доступна агенту для атомарной замены файла. Права, владелец и группа существующего JSON сохраняются, чтобы Xray продолжал читать его после перезапуска.

Откройте HTTPS-доступ к агенту через существующий Nginx с действующим сертификатом. Файл `nginx-location.example.conf` содержит location для включения в HTTPS server block. Замените IP в `allow` на исходящий IP CMS, затем проверьте `nginx -t` и перезагрузите Nginx. Если CMS обращается к частному адресу, включите соответствующий разрешающий переключатель сервера CMS.

Агент слушает только `127.0.0.1:9085`, служебный Xray API — только `127.0.0.1:10085`. Запросам нужны HTTPS, проверенный сертификат и Bearer-токен. CMS запрещает перенаправления, фиксирует проверенные DNS-адреса и ограничивает размеры ответа. В самом агенте доступны только перечисленные операции, пути файлов и имя сервиса поступают из локальных параметров запуска.

Для сверки REALITY приватный ключ передаётся OpenSSL через стандартный ввод в формате PKCS#8. В аргументах процессов ключ отсутствует. Из агента возвращается только вычисленный публичный ключ.

## Передача существующего сервера

1. Обновите VPN-плагин в CMS до 3.3.0. Его обычные подписки продолжат использовать прежние URL.
2. Откройте редактирование подготовленного сервера. Выберите **Xray-core · FIREBALL Agent**, задайте отдельный HTTPS API URL агента и новый токен. Оставьте прежний основной адрес и включённую проверку TLS.
3. В меню сервера откройте **Xray-core · перенос**, нажмите **Проверить перенос**. Предварительный просмотр сверяет UUID или пароль, протокол, порт, Flow, тип транспорта и его основные параметры. Для REALITY агент вычисляет public key из серверного privateKey и сравнивает его с сохранённым, проверяет SNI и shortIds. При несовпадении операция останавливается. Полный серверный JSON дополнительно сверьте с резервной конфигурацией перед переносом.
4. Проверьте число совпадений и недостающих клиентов. После подтверждения сохранённые сроки, квоты и блокировки начинают действовать через агент. Ненайденные входящие подключения остаются для последующего восстановления. Пользователи вне CMS сохраняются в серверном JSON.
5. Выполните восстановление/согласование сервера в плагине. Операции пользуются прежними UUID и паролями. На недоступном узле остаётся повторяемая задача. На доступных узлах подписка продолжает работать.
6. В тестовом клиенте обновите обычную подписку, проверьте каждое подключение, Xray-автовыбор, внешний источник, трафик, отключение и продление. Перезапустите Xray и повторите проверку.
7. После успешной проверки перенесите остальные серверы. Сохраните резервные копии до завершения проверки всех клиентов.

Для нового сервера перед созданием клиентов тоже выполните предварительную проверку и передачу управления. При пустой базе это подтверждает передачу с нулём существующих клиентов. Затем загрузите входящие подключения в CMS и добавьте их в тариф.

## Управление входящими подключениями

На странице переноса после передачи доступны добавление, изменение и удаление inbound. Форма принимает один JSON-объект серверного формата Xray. Тег задаётся как `inbound-25`. Поле `settings.clients` следует опустить, существующие пользователи сохраняются агентом. Создание VLESS + REALITY требует полного корректного блока REALITY с серверным приватным ключом. Приватный ключ нового inbound можно сформировать локально командой `xray x25519` и сохранить на сервере.

Сначала выполните проверку, затем подтвердите применение. Xray проверяет синтаксис до записи файла. Ожидающая применения конфигурация хранится в зашифрованной административной сессии до 10 минут. Для удаления достаточно JSON с тегом и переключателя удаления. Inbound с пользователями удалить нельзя. При редактировании существующие privateKey REALITY и TLS-сертификаты сохраняются при отсутствии соответствующих полей в запросе. Смена протокола существующего inbound блокируется.

Применение входящего подключения заменяет только соответствующий обработчик через Xray API. Его активные соединения могут прерваться. После успешного применения CMS обновляет список входящих подключений. Обновите конфигурации подписчиков через привычное согласование, если поменяли параметры подключения.

## Надёжность и ограничения

- Добавление и изменение клиента, его блокировка и удаление используют локальный HandlerService. После каждой операции агент проверяет результат через работающий API. Операции не перезапускают весь процесс Xray.
- Сначала проверяется и сохраняется требуемая конфигурация. Журнал незавершённой записи в SQLite позволяет восстановить её после сбоя между записью состояния и заменой JSON. До применения runtime возвращается ошибка, если фактическое изменение не подтверждено. Агент повторяет применение в фоне. CMS сохраняет свою очередь повторных операций.
- Неизвестные пользователи сохраняются. Один email на нескольких inbound блокирует перенос для управляемых клиентов, поскольку Xray агрегирует счётчики по email.
- Просроченные и отключённые клиенты удаляются из runtime и из активной части JSON. Метаданные сохраняются в SQLite для продления. Квота проверяется раз в 5 секунд по доступным счётчикам. Общий лимит подписки по нескольким серверам контролирует существующая автоматизация CMS с её интервалом синхронизации.
- Удаление пользователя через HandlerService запрещает новые подключения с его ключом. Открытые соединения могут продолжать передачу до закрытия. Жёсткое завершение активных сессий по сроку или квоте требует отдельной политики отключения. Это ограничение нужно учитывать при выборе режима эксплуатации.
- HWID ограничивает выдачу подписки по устройствам через агент. Уже скопированные UUID продолжают определять аутентификацию в Xray. Положительный лимит устройств при отсутствии `subId` блокирует перенос. Это касается старых VMess и Trojan, которым прежний плагин оставлял `client_sub_id` пустым. Для них требуется расширение идентификации устройств перед переносом с таким лимитом.
- Положительный `ip_limit` блокирует перенос. Xray не предоставляет встроенного аналога панельного ограничения IP на пользователя. Для такого режима нужна дополнительная реализация блокировок активных источников.
- Изменение серверного JSON вне агента блокирует дальнейшие записи до повторной проверки переноса. Смена адресов, портов, приватных ключей или транспорта может потребовать обновления подписки у клиентов.
- Обычные URI, внешние источники и Xray-автовыбор используют существующую генерацию подписки. Ограничения конвертера автовыбора сохраняются.
- Автоматическое обновление бинарника Xray из CMS в эту версию не входит. Ядро обновляется администратором с проверкой конфигурации и резервной копией бинарника.

## Журнал и откат

В журнале плагина появляются события `xray.server_adopted`, `xray.adoption_failed`, `xray.inbound_changed`, `xray.inbound_change_failed`. Обычная очередь записывает события синхронизации клиентов, удаления и трафика. Журнал агента доступен командой `journalctl -u fireball-xray-agent.service`. Он содержит имена операций и фиксированные коды ошибок. UUID, пароли, токены, privateKey и текст вывода Xray в журнал агента не записываются.

После переноса резервируйте также каталог `/var/lib/fireball-xray`, серверный JSON и файл токена. Для файловой копии SQLite остановите агент на время копирования либо используйте SQLite Backup API. В этом состоянии хранятся накопленные счётчики, устройства и очередь применения конфигурации.

Для отката остановите FIREBALL Agent и самостоятельный Xray, восстановите сохранённую конфигурацию и базу прежней панели, запустите прежний сервис. Верните прежний способ управления, URL и токен сервера CMS из резервной копии настроек. Перед восстановлением панели учтите созданных или изменённых после переноса клиентов. Периодические задачи CMS продолжают использовать выбранный backend сервера, поэтому синхронизация должна быть остановлена на время переключения процессов.

## Проверки разработчика

```bash
python3 tests/vpn_native_agent_test.py
python3 tests/vpn_native_agent_test.py --xray /path/to/test/xray
php tests/vpn_native_client_unit.php
php tests/vpn_xray_auto_unit.php
```

Проверки создают временные файлы только в `tests/.tmp` и удаляют свои данные. Сетевые проверки поднимают изолированные процессы на loopback. Проверка на Linux VPS, системного сервиса, Nginx и реальных приложений клиентов выполняется отдельно перед переносом рабочих серверов.

Технические контракты доступны в [документации Xray API](https://xtls.github.io/en/config/api.html), [статистике Xray](https://xtls.github.io/en/config/stats.html) и [реализации команд Xray](https://github.com/XTLS/Xray-core/tree/main/main/commands/all/api).
